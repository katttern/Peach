## Part 0–1. Архітектура Uklon

Масштаб (оцінка з лекції): ~470 тис. поїздок і ~580 млн GPS-пінгів на день.
Streaming: матчинг, surge, трекінг. Batch: звіти, аналітика, навчання моделей.

Шлях однієї поїздки:

1. **Вхід.** Застосунки → ALB. GPS окремо: постійне MQTT-з'єднання з AWS IoT Core, а не HTTP кожні 3 с
   (580 млн пінгів через API Gateway коштували б десятки тисяч доларів на місяць).
2. **Мікросервіси.** Замовлення, матчинг, платежі на ECS Fargate; основна БД Aurora.
3. **Потік подій.** GPS, події сервісів і CDC з БД (через DMS) ідуть у Kinesis Data Streams.
4. **Real time.** Flink рахує surge по районах і алерти. Позиції водіїв у Redis, surge-коефіцієнти в DynamoDB,
   матчинг читає обидва. Push пасажиру через SNS.
5. **Data lake.** Firehose пише сирі події в S3 пачками. Lambda реагує на кожен новий файл: валідація.
6. **Batch.** Нічний Glue job робить Parquet. Glue Data Catalog тримає схему, Athena дає SQL, Amazon Quick дашборди.
7. **ML.** SageMaker навчає моделі ETA і попиту на даних із S3, сервіси викликають розгорнуті моделі.

Питання:

- Що станеться, якщо real-time дорога відстане на 10 хвилин? А batch на добу?
- Чому GPS не йде через Lambda?
- Що маленький стартап викине першим і що при цьому втратить?

## Part 2. Batch на AWS

### Датасет

Рядок = одна webhook-подія, тобто зміна статусу платежу. Один платіж дає 2–3 події: `created → processing → success | failure`.
~1% подій приходять двічі, ~2% запізнюються на 1–10 хв.

| Поле | Приклад | Значення |
|---|---|---|
| `invoiceId` | `p2_9ZgpZVsl3` | платіж, спільний для всіх його подій |
| `status` | `failure` | `created`, `processing`, `success`, `failure` |
| `failureReason` | `Insufficient funds` | лише для невдалих платежів |
| `amount`, `finalAmount` | `45000`, `0` | у мінорних одиницях (копійки, центи); `finalAmount` ≠ 0 лише при `success` |
| `ccy` | `980` | ISO 4217: 980 UAH, 840 USD, 978 EUR |
| `reference` | `84d0070e…` | id замовлення в мерчанта |
| `createdDate` | `2026-10-01T08:15:22Z` | коли платіж створено |
| `modifiedDate` | `2026-10-01T08:15:31Z` | коли стався цей статус (**event time**) |
| `receivedAt` | `2026-10-01T08:15:32Z` | коли подія дійшла до нас (**processing time**) |
| `merchantId`, `merchantName`, `mcc` | `m-002`, `Supermarket`, `5411` | кому платили, код категорії |
| `customerId`, `paymentMethod`, `device` | `u-0012345`, `apple_pay`, `ios` | хто платив і як |

Обсяг: жовтень 2026, 1 млн платежів, ~3 млн подій, 1.2 GB JSON Lines, партиції по днях:
`s3://ucu-ooad-lab8-payments/payments/dt=2026-10-01/events.jsonl` … `dt=2026-10-31/`.

Бакет публічний на читання. Весь префікс `payments/` копіюємо у **свій** бакет в `us-east-1` через AWS CLI
(усередині регіону безплатно). Таблиця, краулер і результати живуть у своєму акаунті.

Формат імітує webhooks monobank acquiring (`invoiceId` … `reference`, обидві дати); решту полів додано для аналітики.

### Way A: таблиця і запити в Athena

Спочатку дедуплікація, усі наступні запити читають дедуплікований view.

1. **Таблиця.** External table `payment_events` над своєю копією `payments/`: JSON SerDe, усі поля, `dt` як партиція.
   Завантажити партиції, перевірити `COUNT(*)` ≈ 3 млн.
2. **Дедуплікація.** View `payments`: рівно один рядок на `invoiceId`, з найпізнішим `modifiedDate`.
   Спочатку прибрати точні дублікати.
3. **Оборот** по мерчанту і валюті, лише успішні платежі, у гривнях (доларах, євро), а не в мінорних одиницях.
4. **Failure rate.** Частка невдалих платежів по `paymentMethod` і `device`, від найбільшої.
5. **Пікові години.** Кількість платежів за годиною доби.
6. **Запізнілі події.** Скільки подій прийшло пізніше ніж за 60 с після події (`receivedAt − modifiedDate`), із скількох.
7. **Parquet.** CTAS: дедупліковані платежі в Parquet, партиції по `dt`, префікс `curated/` свого бакета.
   Запити 3–5 виконати і на Parquet-таблиці.

### Way B: Glue Crawler

Запустити краулер над `payments/` і порівняти схему зі своєю:

- Які типи він вибрав для `amount`, `ccy` і дат? Чи розпізнав `dt` як партицію?
- Що сталося з `failureReason`, який є лише в частини подій?
- Яка схема зручніша для запитів і чому схеми вручну досі поширені?

### Що здати за Part 2

- Масштаб: скільки унікальних `invoiceId`, скільки дублікатів, яка частка подій запізнилась більш ніж на годину.
- Результати запитів 2–6.
- Data scanned і час виконання запитів 3–5 на JSON і на Parquet. У скільки разів дешевше?
- Пояснення: чому `DISTINCT` іде перед `row_number()` і що ламається без дедуплікації.

## Part 3. Streaming локально: Redpanda + Python

Схема: один день із S3 (`events.jsonl`) → Producer (Python) → Redpanda → Consumer (Python, вікна по 1 хв event time)
→ алерт; Redpanda Console поруч.

- **Redpanda.** Redpanda і Redpanda Console у Docker Compose, топік `payments` на 3 партиції, Console на `localhost:8080`.
- **Producer.** Один день подій, replay у порядку `receivedAt`, ~20 платежів за секунду. Ключ повідомлення `invoiceId`,
  щоб усі події платежу йшли в одну партицію.
- **Consumer.** Відкинути дублікати, рахувати частку `failure` по `paymentMethod` у хвилинних вікнах event time
  (`modifiedDate`), друкувати алерт, якщо вона > 10%. Вікно закривати через 2 хв після його кінця, щоб дочекатись запізнілих.

Експерименти:

1. Зупинити consumer на хвилину і запустити знову: подій не втрачено, бо Kafka тримає лог.
2. Два consumer в одній групі: у Console видно, як вони ділять партиції.
3. Producer валить 30% платежів: спрацьовує алерт.
4. Час очікування запізнілих = 0: порахувати, скільки подій відхилено як запізнілі, і що змінилось у числах вікон.

На заняття: множина побачених подій росте без меж. У продакшені вона живе в Redis або стані Flink із TTL.

## Part 4. Самостійно: streaming у хмарі

Відтворити пайплайн зі схеми. Дані: той самий датасет або свій продукт (доставка, музика, IoT тощо).

Схема з умови:

```
Producer (Python, laptop або Lambda)
  └─> Kinesis Data Streams (on-demand)
        ├─> Data Firehose (буфер 60 с) ─> S3 payments-stream/ ─> Glue Crawler + Data Catalog ─(schema)─> Athena
        └─> AWS Lambda (перевірка failure rate) ─(failures > 10%)─> Amazon SNS (email-алерт)
```

Здати:

- діаграму свого пайплайна (якщо продукт інший, пояснити, звідки дані);
- код продюсера;
- скриншот запиту Athena по даних, що пройшли через стрім;
- коротко: чим хмарний пайплайн відрізняється від локального Redpanda і скільки це коштувало.

**Після завершення видалити Kinesis stream і Firehose stream:** Kinesis тарифікується щогодини.

## Примітки (наші висновки, не текст умови)

- Умова каже про запізнення 1–10 хв, але просить частку подій із запізненням понад годину. Очікуємо число, близьке до нуля;
  перевірити запитом, а не припускати.
- Один день ≈ 32 тис. платежів, тож replay на 20 платежів/с триває ~27 хв. Закладати це на кожен експеримент.
- Replay стискає добу приблизно в 50 разів, тому 2 хв очікування треба міряти в event time (watermark), а не годинником.
- Запізнення до 10 хв більше за очікування у 2 хв, тож частина подій буде відхилена і в базовому режимі.
